# AI Optimization Report

## 1. Tools & Prompting

- **Tools Used:** Anthropic Claude (Chat) & Cursor / ChatGPT for scaffolding, relational schema modeling, API route architecture, defensive server validation, high-contrast Tailwind UI design, and Vitest test suite creation.
- **Workflow & Iterative Prompting:** 
  - Fed the factory domain constraints and separation-of-duties matrix directly into the model to define strict Prisma schemas and deterministic state transitions.
  - Used conversational chain-of-thought prompting: broke the delivery into isolated modules (Schema -> RBAC Endpoints -> Verification Engine -> Sewing Isolation -> Vitest Cases).
  - Executed every command locally, inspected the resulting payloads via network logs and Postman, and prompted the AI iteratively with runtime stack traces and compile errors.

## 2. Flawed / Broken AI Code

1. **Prisma CLI / Config Version Incompatibility:**
   - *Issue:* The generated script pinned Prisma v6, but running `npx prisma init` pulled Prisma v7 templates creating an unneeded `prisma.config.ts` and dumping client bindings to `src/generated/prisma`. Peer dependency conflicts also forced fallback targets.
   - *Fix:* Removed the superfluous configuration files, normalized dependencies with `--legacy-peer-deps`, unified Prisma Client generation under standard `@prisma/client`, and restored the target connection string inside the Neon cloud instance.

2. **Vitest Tooling & Missing Peer Dependency:**
   - *Issue:* Initial test scaffolding configured `vitest` without explicitly resolving its core `vite` runtime engine due to dependency flags, leading to an immediate failure upon executing `npm test`.
   - *Fix:* Explicitly installed `vite` and `vitest` as dev-dependencies and configured custom route mock contexts to execute route handler integration tests directly.

3. **Client-Side Verification Trust & Numeric Coercion Hallucination:**
   - *Issue:* The initial AI-generated verification route trusted the `status` flag (`GREEN`/`RED`) passed in the client JSON payload and performed loose JavaScript coercion `Number(qty)` (which dangerously evaluates empty strings `""` to `0` and accepts negative signs `-` and exponential values `1e5`).
   - *Fix:* Stripped status calculations from the client payload entirely. Enforced strict Regex numeric parsing on the server (`/^\d+$/`) and mandated that the backend re-calculates all traffic-light statuses dynamically from raw database items before authorizing batch completion.

4. **White-on-White High-Contrast Defect in Dropdowns & Inputs:**
   - *Issue:* Tailwind styling generated by the AI defaulted to ambient CSS variable references that caused input text and select options to render white-on-white on light-mode factory workstations.
   - *Fix:* Manually overrode input base classes with explicit dark foreground text (`text-slate-900 bg-white border-slate-300 focus:border-blue-600`) across all input, focus, and dropdown states to ensure zero-defect accessibility compliance.

## 3. Human Refactoring

- **Server-Side Hard-Stop Engine:** Completely decoupled approval permissions from UI button states. Even if a compromised client sends a direct `POST` to `/api/orders/[id]/approve`, the backend independently audits all component rows inside a transactional query. If even one component has `actual_qty < expected_qty`, the server halts with `422 Unprocessable Entity`.
- **Identity Isolation & Immutable Audit Trails:** Refactored the verification logging system to strictly extract the `verifier_id` from the decoded session token/JWT rather than accepting user IDs from the request body. Once verified, the database lock writes the verifier ID, server timestamp, and fabric wastage variance immutably.
- **Defensive Input Validation:** Replaced standard HTML5 `type="number"` with `inputMode="numeric"` combined with server-side validation schemes to block invalid payloads, floats, and negative numbers.
- **Atomic State Transitions:** Converted raw status assignments into database atomic compare-and-set updates (`WHERE id = orderId AND status = 'PENDING_VERIFICATION'`) to prevent concurrency race conditions on the factory floor.

## 4. Defensive Architecture

- **Unified RBAC Guard:** Created a higher-order handler (`handle([...roles], fn)`) protecting all mutating endpoints:
  - Missing/invalid session $\rightarrow$ `401 Unauthorized`
  - Persona mismatch (e.g., `cutting_supervisor` attempting approval or `sewing_supervisor` attempting order creation) $\rightarrow$ `403 Forbidden`
- **Zero-Trust Hard Stop:** `approveOrder` executes inside an atomic database transaction. It verifies each component against expected recipe BOM multipliers; any missing count or shortage (`RED`) aborts the write with `422 Unprocessable Entity`.
- **Strict Query Isolation:** The Sewing Queue endpoint (`GET /api/sewing/queue`) enforces `WHERE status = 'VERIFIED'` directly in the database query. Client query parameter manipulation cannot leak unverified or rejected cutting batches.
- **Integration Test Coverage:** Vitest suites run against real route handlers and database mocks, rigorously validating the 401, 403, and 422 boundary contracts under adversarial payloads.
